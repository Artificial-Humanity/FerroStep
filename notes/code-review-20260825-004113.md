## 1. The audit invents an escalation and a release out of one rescope

**`ferrostep-cli/src/main.rs:515` and `:522`** · correctness · **confirmed by
execution**

`render_audit` counts escalations as *any decision whose `to` is a halted
state*, and releases as *any event whose `from_state` is a halted state*:

```rust
Decision::Allow { to, .. } => def.halted.contains(to),          // escalations
e.event.from_state.as_ref().is_some_and(|s| def.halted.contains(s))  // releases
```

A rescope is `Decision::Allow { to: <the state it is already in>, .. }`
(`ferrostep-core/src/lib.rs:862`), and `do_rescope` sets
`from_state: Some(<that same state>)`. So rescoping a record that is sitting
in a halted state satisfies **both** tests at once, and the record never
moved.

Measured, by temporarily adding a probe to the CLI's own test module against
its own `seeded()` fixture (probe reverted; tree is clean):

```
BEFORE:  record 2: escalated  [NEEDS PERSON]  2 move(s) · 1 escalation(s) · 0 release(s)
AFTER :  record 2: escalated  [NEEDS PERSON]  3 move(s) · 2 escalation(s) · 1 release(s)
```

One rescope; both counters wrong.

**Why this one matters more than its size.** B4's done-when is *"a person
reviews a real merge from the report alone."* The failure is not a crash or a
visible nonsense number — it is a **plausible false story**: the report says
this record escalated a second time and somebody released it. A reader has no
way to tell that from the real thing, and the audit is specifically the
surface offered to someone who is *not* opening a database console to check.

**It is reachable in the only real deployment.** The first migrating loop's
definition carries `halted: ["escalated"]` and a `rescopes` rule in the same
file. Rescoping a paused record is an ordinary thing to want — a record
parked for a person is exactly the kind that gets moved to another unit of
work.

**Note the root cause is a design tension, not a typo.** `authorize_rescope`
deliberately returns `to: <current state>` so that callers persist it through
the one atomic path they already have — that reasoning is sound and
documented. The cost is that the history now contains events where
`from_state == to`, and every reader that infers movement from those fields
inherits the ambiguity. The two counters here are the first two readers.
`decided_scope_updates(...).is_empty()` distinguishes them cleanly, and is
already the test the PocketBase adapter uses for the same purpose
(`ferrostep-pocketbase/src/lib.rs:529`).

## 2. The README documents about a third of the product

**`README.md`** · product-alignment

The Layout table names three crates. The workspace has nine. Counting
mentions anywhere in the file:

| mentioned | not mentioned anywhere |
|---|---|
| `ferrostep-core`, `ferrostep-py`, `ferrostep-github` | `ferrostep-cli`, `ferrostep-ledger`, `ferrostep-sqlite`, `ferrostep-pocketbase`, `ferrostep-notify`, `ferrostep-roster` |

Also absent: the strings *SQLite*, *PocketBase*, *scope*, *rescope*,
*config.yaml*, *agent-env*. The `Building` section stops at the core tests
and the Python wheel — a reader is never told the `ferrostep` binary exists,
and it is the only thing here a person actually operates.

Everything 0.1.0 shipped, and everything shipped since, is invisible on the
page AGENTS.md calls "the product description."

**Against the project's own bar this is the most consequential finding in the
review.** The baseline is defined as done when two sentences are true, and
the second is *"a stranger can read this repo and run their own loop on their
own database by imitation."* A stranger reading this README learns that
FerroStep is a Rust engine with Python bindings and no way to store anything.
The first half of the bar is essentially met; the second is not merely
incomplete, it is contradicted by the front page.

This is also the concrete form of the deferral I took on adopter
documentation. Two friction entries (#6 authoring a definition, #9 the roster
bootstrap) point at a missing adopter guide, but they sit downstream of this:
the guide has nothing to link back to while the README does not admit the
adapters exist.

## 3. `ferrostep-py` never got rescope, and nothing says so

**`ferrostep-py/`** · parity · unacknowledged

Occurrences of `scope` per crate:

```
ferrostep-core 68 · ferrostep-cli 22 · ferrostep-sqlite 17 · ferrostep-pocketbase 16
ferrostep-ledger 3 · ferrostep-py 0
```

The bridge exposes `authorize`, `authorize_create`, `next_moves`, `status`,
`workflow_json`. There is no `authorize_rescope`. A Python consumer cannot
referee a scope change at all — the operation friction entry #4 exists to
make impossible-to-do-rawly is, from Python, still only doable rawly.

Nothing in `CHANGELOG.md`, `docs/`, or `notes/rescope-design.md` mentions
this. It reads as an oversight rather than a deferral, which matters because
the repo has a strong and well-kept habit of deferring things *out loud*
(`ferrostep-ts`, `workflow/skills/`, `skills/` — each absent with a written
reason). This is the one gap that is merely silent.

AGENTS.md: *"the Python bindings are a first-class citizen."* Right now the
Decision JSON contract is a superset of what the first-class binding can
produce.

## 4. The shared scope helper is the one with no test

**`ferrostep-ledger/src/lib.rs:170`** · test-coverage

`decided_scope_updates` has zero test references anywhere in the workspace —
only its definition and three adapter call sites. Its sibling
`decided_snapshot` is covered by
`a_decision_becomes_the_snapshot_it_promised`, which checks all three
decision kinds.

The crate's own doc-comment is the argument for why this matters: the helper
exists as one implementation *"because two copies of 'what does applying
mean' would be free to disagree."* The half that is asserted is tested; the
half that was added later is not.

## 5. No shipped example uses `rescopes`

**`examples/`** · test-coverage, product-alignment

Neither `review-loop.json` nor `product-review.json` carries a `rescopes`
block. Two consequences:

- `shipped_examples_stay_valid` — the guard AGENTS.md names as what keeps
  `examples/` honest — never validates a definition containing a rescope
  rule. The core's rescope validation (`UnknownRescopeRole`,
  `DuplicateRescope`) is exercised only by unit tests written against
  hand-built definitions.
- The newest concept in the engine, and one AGENTS.md now lists as a standing
  convention (*"Scope is refereed like everything else, and default-deny"*),
  has no illustration a reader can copy.

## 6. Second opinion on the open question in friction #11

Entry 11 leaves open whether the heading `## What the engine guarantees` is
the same defect as "enforced."

**The heading is fine. A bullet underneath it is not.** Applying that entry's
own test — refuse the halves, demand the end state, singular:

> **Loop ceilings that survive crashes.** Counters spend on *entry* to work
> (claiming a pass costs it), so an agent that crashes mid-pass has already
> paid. **A crash loop cannot become an infinite loop.**

That last sentence is a claim about a deployed system, not about the engine's
answer. The engine guarantees it *reports* the spend; whether the loop is
bounded depends entirely on a caller persisting the flip and the counter in
one atomic write — which the README itself says, 26 lines further down under
"What FerroStep is not," and which the Python docstring says outright
(*"Splitting that write breaks the crashed-pass-still-costs-one guarantee"*).

So it is the identical shape as the "enforced" defect: an unqualified promise
in the pitch, correctly qualified far below where a skimmer stops. Entry 11's
lesson generalized one step further is that **the pitch is where this project
loses precision, and it has now happened twice in the same paragraph
cluster** — worth treating the README's top third as a surface with its own
review bar rather than as prose.

The other bullets survive the test: workflows-as-data, exhaustion-is-routing,
ending-vs-pause, role-gating, exists-vs-would-fire, counters-belong-to-the-
operator, and purpose-travels are all properties of the engine's own answers.

## 8. `explain` panics on a maximal ceiling

**`ferrostep-cli/src/main.rs:309,311`** · robustness · low

`c.max + 1` on a `u32` read from the definition. With `"max": 4294967295` this
is `attempt to add with overflow` — a panic in a debug build, a wrap to `0` in
release (which would print *"search your tree for 4294967295 AND for 0"*).

Genuinely low: nobody writes that ceiling on purpose. Recorded because
`explain` is the subcommand aimed at the person who has not got the system
working yet, and a panic is the least useful thing to hand them. A saturating
add costs one word.

## Not findings — checked and sound

Recorded so a later reader knows these were looked at rather than skipped.

- **The SQLite apply path.** `IMMEDIATE` transaction, scope labels read and
  merged inside it, and state + counters + scope + version written by a
  single `UPDATE` carrying the compare in its `WHERE`. The reasoning in the
  comments matches what the code does, which is not always true of comments
  this confident.
- **The capability negotiation.** `writes_scope` read from the ping at
  connect, refusal by name with the remedy in the message, and the default
  test fixture is deliberately the *old* ping. That last choice is what makes
  the refusal testable on both sides.
- **The roster's fail-loudly posture.** Every path to an emitted value goes
  through `require_persona_file`, so no output format can be the one that
  skips the check; `shell_quote` is applied to every emitted value and the
  keys are literals rather than derived. The hostile-title test runs through
  a real shell.
- **`Decision::Allow`'s growth.** `skip_serializing_if` on `scope_updates`
  means a pre-rescope consumer reads byte-identical JSON. The convention it
  established (grow a kind's fields, not the set of kinds) is applied, not
  just written down.
- **Counters are not partially spent on an exhausted decision** — the early
  return discards `counter_updates` built so far.

## Shape of the whole

Six of the eight findings are downstream of two events, and it is worth
naming them rather than treating the list as unrelated defects.

**Rescope landed fast and its blast radius was under-swept.** Findings 1, 3,
4 and 5 are all the same omission wearing different clothes: the core got the
feature, the two adapters got it, the CLI got it — and the *readers* of what
it produces (the audit), the *other binding* (Python), the *shared helper's
tests*, and the *examples* did not. The friction file records that migrating
a ceiling leaves derived arithmetic behind (entry 13); this is the same
lesson pointed inward. Adding an operation leaves derived *consumers* behind,
and they do not contain the name of the thing that changed either.

**The front page stopped tracking the product around 0.1.0.** Findings 2, 6
and 7 are all the pitch and the status text aging while the code moved. This
is the specific, checkable form of the thing that is otherwise easy to state
vaguely: the repo's second baseline sentence has no owner.

If any of this becomes work, finding 1 is the one to take first — it is
small, it is confirmed, it corrupts a report a person is meant to trust, and
it is live in the only deployment there is.
